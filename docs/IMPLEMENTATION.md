# Реализованный MVP и правила расчётов

## Архитектура

- `main.py`: ручной запуск, блокировка повторного процесса с той же рабочей папкой, окно WebView2, обработка закрытия.
- `frontend/src`: React-интерфейс. Две равные подвкладки, история переходов внутри страницы, мастер, просмотр результата, копии, скрываемый журнал.
- `shoko/server.py`: локальный HTTP API, случайный токен каждой сессии, проверка Host/Origin, отсутствие внешней публикации.
- `shoko/engine.py`: этапы, отмена, проверки, сохраняемый план и единственное подтверждение записи.
- `shoko/docx_rules.py`, `docx_sources.py`: действующие расчёты и чтение DOCX/RTF; `calculation.py`/`mappings.py` сохранены как справочная альтернативная реализация и общие утилиты, основной запуск их calculate не вызывает.
- `shoko/adapters.py`: XLSX/CSV, локальная цель и Google Sheets.
- `shoko/storage.py`: атомарное сохранение настроек/планов, копии и контрольные суммы.
- В 0.1.0 CSV Гаража выбирается вручную. Telegram-клиент, авторизация и автоматическая отправка/скачивание удалены. Telegram и расписание планируются для второй версии.

На Windows `main.py` включает truststore до импорта сетевых компонентов: HTTPS использует системные доверенные сертификаты, сохраняя проверку цепочки и имени узла. Сетевые ошибки Google классифицируются без раскрытия исходных JWT/ключей. Проверка целевой Google-таблицы запрашивает метаданные и наличие обязательного листа, без получения ячеек; снимок содержимого остаётся частью подготовки и проверки перед записью.

## Выбранная логика

С 19.10.2026 активен согласованный профиль DOCX + три RTF. Точные исходники, имена файлов, диапазоны, формулы, исключения и намеренные отличия: [DOCX_RTF_PARITY.md](DOCX_RTF_PARITY.md).

После «Обновление» открывается меню с галочками и «Выбрать всё». Одна кнопка «Обновить» готовит точный общий план только отмеченных операций; обязательное подтверждение, хеши исходников, полная копия и сверка сохранены. Старый первичный Python-расчёт в этой цепочке не вызывается. Некорректные данные не превращаются в нули; строки CSV остаются текстом даже при начальном знаке `=`.

## Копии и сбои

Существующий XLSX копируется целиком. Для Google через Drive files.copy создаётся полная самостоятельная Google-таблица в явно выбранной папке Google Drive. Тип диска (личный или общий) не ограничивается приложением. Передаётся copyComments=true: сохраняются текущие открытые комментарии и ответы; закрытые обсуждения по согласованию пользователя не архивируются. Проверяются права создания в папке и canCopy источника, тип файла, родительская папка и маркер происхождения, структура всех листов, содержание и количество текущих комментариев/ответов, их привязка к ячейкам через Sheets commentsViewMode. Версия Drive и комментарии исходной таблицы сверяются после копирования; версия повторно проверяется непосредственно перед записью. Google поддерживает два способа: OAuth Desktop app от имени пользователя (по умолчанию) и прежний сервисный аккаунт. Оба используют scopes spreadsheets и drive; нужны включённые Sheets/Drive API и права выбранного аккаунта на таблицу и папку. Для существующей таблицы/папки по ссылкам drive.file без отдельного Google Picker недостаточен. OAuth идёт во внешнем браузере, PKCE S256, callback HTTPServer на 127.0.0.1 со случайным портом, проверкой Host/path/state и таймаутом 180 секунд. Callback и raw OAuth-ошибки не журналируются. Токен и refresh token хранятся в sessions/google.vault под Windows DPAPI, автоматически обновляются в том же файле. Публичное состояние показывает только почту и наличие входа. OAuth-клиент привязан к сессии хешем конфигурации. Переподключение/выход отменяют план; перед записью дополнительно сверяется идентификатор Google-аккаунта. Выход удаляет локальное сохранение, без глобального отзыва разрешения. Ошибки HTTP различают квоту, API, права и лимиты без раскрытия payload. Ограничение общего диска не вводится. Настройки атомарно заменяются в единственном settings.local.json без резервного копирования. Сохранение неполного набора полей разрешено, проверки обязательных источников выполняются отдельно и перед обновлением. Старый признак незавершённого мастера при наличии заполненных полей мигрируется без потери данных. При создании новой рабочей копии книги фиксируется отсутствие предыдущего файла.

Локальные копии имеют manifest и контрольные суммы; недоступная/повреждённая копия блокирует запись. Для Google локально хранятся только сведения о копировании и результатах проверки, а сама полная таблица остаётся в Google Drive. Проверенная Google-копия открывается в браузере; локальный XLSX скачивается в ZIP и восстанавливается вручную из original.xlsx. Восстановление через приложение не реализуется по запросу пользователя. Страница копий показывает полные Google Drive-копии; старые локальные JSON-снимки не выдаются за полную облачную копию. Ошибка копирования сохраняет статус failed и известный ID копии. Создание после неизвестного таймаута автоматически не повторяется, возможный незавершённый результат остаётся для проверки в папке Drive. Незавершённое копирование после перезапуска отмечается ошибкой, а не вечной загрузкой.

Сетевая ошибка при записи/сверке помечает результат «требует проверки»; копия сохраняется. Автоматический повтор записи не выполняется. После аварийного завершения статус `writing` становится `interrupted`. Нельзя гарантировать отсутствие чужой правки Google между последним чтением и batchUpdate: пользователь должен исключить одновременную работу в тестовой копии.

Проверка XLSX/CSV и лимиты выполняются до расчётов. CSV ограничен 30 МБ, читаемые матрицы — 2 млн ячеек, начисления — 100 000 строк / 50 столбцов, план — 500 000 изменений, часть записи Google — до 2 МБ компактного UTF-8 JSON до сжатия. Большой план отправляется последовательными частями без усечения данных.

Рабочий снимок Google запрашивает через fields только значения, формулы, идентификаторы и размеры нужных листов. Полное оформление ячеек не скачивается и не дублируется в metadata; структура остальных листов сохраняется для контроля изменений и выбора свободного sheetId. Fingerprint учитывает структуру и userEnteredValue, включая формулы, без изменчивого результата их пересчёта. Концевые пустые значения нормализуются. Полная Google-копия с оформлением и текущими комментариями по-прежнему создаётся отдельным Drive files.copy.

Планы сохраняются атомарно в plans/<id>.json.gz: компактный UTF-8 JSON, gzip, контрольная сумма исходного содержимого и fsync перед заменой. При чтении проверяется формат/целостность gzip и предел распакованного JSON 128 МиБ. Небольшие старые JSON-планы читаются; старые многогигабайтные планы не загружаются целиком. Настройки и копии не переводятся в этот формат. Пользователь готовит новый план после установки исправленной сборки; существующие планы и облачные копии не удаляются.

Соседние изменённые ячейки объединяются в точные прямоугольные блоки updateCells по нескольким строкам. Пропуски между изменениями не заполняются; формулы нетронутых ячеек сохраняются. Меняется только userEnteredValue, входящие строки со знаком = остаются текстом. Размер проверяется по фактическому компактному UTF-8 payload до предпросмотра и повторно до резервного копирования. После подтверждения и проверки полной копии отправляются подготовленные части batchUpdate с ожиданием ответа до 180 секунд (соединение/передача до 45 секунд). Размер и число частей входят в подтверждённый план. Атомарна каждая часть; весь процесс не является одной транзакцией. Пропуски, типы значений, формулы и точные адреса сохраняются при делении прямоугольника по строкам или широкой строки по столбцам. Все части проверяются до предпросмотра и до бекапа. Автоматических повторов мутаций нет.

Обработчики сообщают об отсутствии файла, листа, формулы, неверном CSV, недоступности Google, таймауте и невозможности записи. Источники не изменяются. Подготовка отменяется между этапами; сетевой запрос может завершиться по своему таймауту. Успешные промежуточные этапы после отмены повторно не используются: новый запуск готовит новый план.

Сверить F/G/H и исторические колонки с эталоном заказчика и вручную выбрать подходящий CSV Гаража. Внутренний Google-проект изучен 15 октября 2026 года; основной процесс Гаража перенесён в приложение, см. GARAGE_PROCESS.md. Технические интеграционные проверки на копиях не заменяют бизнес-приёмку реального автопарка.

## Передача подтверждённой записи Google

Для JSON batchUpdate от 64 КБ используется HTTP Content-Encoding: gzip, если это уменьшает объём. Размер каждой части до 2 МБ проверяется до сжатия и до создания копии. После распаковки содержимое полностью совпадает с подготовленной частью JSON. Запросы идут последовательно, с интервалом между началами не меньше 1,2 секунды. Подтверждение, проверки исходников/цели/аккаунта, создание и проверка полной копии с текущими комментариями и последующая сверка значений сохранены.

Таймаут записи — (45, 180): 45 секунд на подключение и сокет передачи, 180 секунд ожидания данных ответа. Раньше на сокет передачи распространялся короткий connect timeout 10 секунд, несмотря на read timeout 180. Таймауты являются сетевыми лимитами ожидания, а не общим дедлайном операции. Статусные GET по-прежнему используют (10, 45). Сжатие тела запроса не отключает HTTPS и не меняет корпоративные прокси или защиту.

Журнал показывает начало повторной проверки после копии, начало записи, размеры JSON и сетевого тела, переход к сверке и точный неуспешный этап. Сетевая ошибка POST batchUpdate всегда сообщает, что запись не подтверждена и могла примениться; автоматического повтора нет. В публичную ошибку включаются только имена типов исключений и числовые errno/winerror, включая вложенные ошибки urllib3. Текст исключений, URL, заголовки, токены и тело запроса не журналируются. История сохраняет причину и этап со статусом uncertain; новый запуск требует нового плана и подтверждения.

## Одинаковые входные данные при повторном запуске

Проценты RTF в V/Z/AC сохраняются числами, эквивалентными результату старого USER_ENTERED, с округлением до 0,1 процентного пункта. Они не преобразуются в текст «0.0%». Неизменные файлы и дата после успешной записи не создают новые изменения, BF или полную копию. Проверены повторные запуски и перезапуск процесса.

## Учёт объединений в плане

Снимок и лёгкая проверка метаданных читают sheets.merges без оформления ячеек. Объединения входят в fingerprint и повторную проверку непосредственно перед записью; их изменение после просмотра требует нового плана. Показатели вычисляются профилем docx-rtf-v1.

Перед построением списка изменений и предпросмотра нормализуется только выходная матрица: у объединённого диапазона записывается верхняя левая ячейка. Пустые позиции внутри объединения не записываются. Служебные нули типов int/float и строки «0»/«0.0%» в остальных позициях заменяются пустыми с явным предупреждением о количестве на листе. Исходники, верхние левые значения и сами объединения не меняются. Другие непустые значения в недоступной позиции блокируют подготовку с адресом ячейки; значимые данные не отбрасываются молча.

prepare_write дополнительно отвергает любой уже просмотренный план, содержащий запись в подчинённую позицию объединения, даже ноль или очистку. Во время записи план не фильтруется. verify сверяет весь точный нормализованный план, наличие листов и неизменность объединений; ошибки обычных ячеек и верхних левых ячеек объединений по-прежнему блокируют успешное завершение. Старые ошибочные планы и история автоматически не переписываются.

## Кеш состояния Google

Для интерфейса кешируются только почта/флаг подключения/сообщение. Ключ кеша содержит путь выбранного OAuth-клиента и сигнатуры его файла и защищённого vault (mtime/ctime/размер/идентификатор файла). Кеш сбрасывается при сохранении и отключении аккаунта. Это снижает частоту DPAPI-расшифровки во время polling и не служит решением о допуске к Google: session и identity всегда вызывают полную загрузку, проверку client fingerprint, refresh token, scopes и token_uri. Изменения настроек, аккаунта, источников, цели и подтверждённого плана блокируют запись прежними проверками. Текущая поставка использует отдельный официальный Python; сведения о прежнем срабатывании и границах проверки находятся в WINDOWS_DISTRIBUTION.md.


### Копии BF и диагностика (0.1.0)

`sheet_backups` содержит только имена источника и копии; матрицы данных в плане не дублируются. Учитываются прямые изменения ячеек, переименование рабочего Гаража по прежней логике и изменения вычисляемых J:O. Новые листы без прежнего состояния не копируются. Отсутствие изменений не создаёт новых BF-листов. Имена не пересекаются с существующими, сравниваются без учёта регистра; повторные имена получают московскую дату/время и при необходимости номер.

После проверки полной резервной копии упорядоченная последовательность Google batchUpdate сначала выполняет duplicateSheet для всех BF, фиксирует прежние результаты формул в копиях и затем применяет подтверждённые изменения. Эта последовательность сохраняется на границах частей; последующие части не отправляются после ошибки. BF и архивы вставляются непосредственно после своего источника с учётом всех предыдущих вставок. Исходные sheetId сохраняются. Оформление и примечания копируются нативно. Исходные формулы и текущие обсуждения сохраняет полная копия Drive. После записи проверяются содержимое, размер и объединения BF-листов, затем действующие листы и расчёты. Локальный XLSX использует copy_worksheet, сохраняя формулы, оформление и примечания; библиотека не пересчитывает формулы.

Google-диагностика хранит последние 100 ошибок запросов: фиксированное название операции, HTTP/безопасный код причины, классы транспортных исключений, реальные таймауты, длительность и номер попытки. URL, ID документов, тела запросов/ответов и ключи в отчёт не попадают. Повтор допускается только для прежних временных транспортных сбоев GET; мутации не повторяются. Подсчёт места ограничен 8 секундами/100 тысячами файлов, не следует по ссылкам и junction, ничего не удаляет.


### Поэтапная запись Google (0.1.0, 16.10.2026)

Перед подтверждением интерфейс показывает число частей и предупреждение о частичном результате при сбое. До каждого POST в plans/<id>.result.json атомарно сохраняются общее число частей, число подтверждённых Google частей и номер отправляемой части; после успешного ответа обновляется счётчик. При ошибке соединения состояние отправляемой части считается неизвестным, следующие части и автоматический повтор заблокированы. Полная копия Drive и уже созданные BF-листы сохраняются; пользователь проверяет таблицу и готовит новый план. После перезапуска незавершённый результат отмечается interrupted с последним сохранённым прогрессом, без автоматического продолжения. Статус done и статистика успешных обновлений появляются только после общей сверки всех изменённых ячеек, BF-копий, структуры и вычисляемых значений.


### Согласованные новые модели и динамический состав (19.10.2026)

Действующие уточнения DOCX/RTF перечислены в DOCX_RTF_PARITY.md. fleet_by_model ищет блок/год по содержимому, проверяет поля выбранного дня и запрещает неоднозначность. Обычные и каршеринговые Polo/Octavia 2019 независимы во всех периодах. Исходная fleet_day сохранена только для независимого эталона старого RTF. model_rows создаёт только две согласованные целевые строки и одну строку Tenet Гаража; model_rows и row_templates входят в checksum плана. copyPaste использует PASTE_FORMAT, затем применяются исключительно просмотренные изменения. Расширенный виртуальный снимок служит расчёту; архив берётся из исходного реального состояния. Новые связи заполняют только пустые J:O согласованных моделей; существующая собственная логика сохраняется. После полной копии повторно проверяются источники, затем выполняются BF и запись. Новые строки показываются отдельным блоком предпросмотра.


### Удаление предпросмотра (19.10.2026)

По запросу пользователя удалена отдельная страница предпросмотра и таблицы «Было → станет»/полного результата. После подготовки остаётся компактное подтверждение даты и выбранных операций. Подтверждение передаёт id/checksum именно подготовленного плана; автоматической записи нет. При нулевых изменениях показано сообщение без кнопки записи. Предупреждения исходников и многочастной записи остаются видимыми. Внутренний статус preview сохранён как техническое состояние готовности, чтобы не менять защиту одноразового плана, бекапы и итоговую сверку.

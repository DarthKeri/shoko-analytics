MVP повторял эту зависимость. При первом переносе шапка менялась, на следующем запуске обнаруживались дополнительные процентные колонки: те же 10376 нулей уже выводились как «0.0%». Это преобразование представления, а не новое начисление. Дополнительным источником ложных изменений было строгое различение int и float после сериализации в Google/Excel.

Исправление: assemble_prostoi сначала собирает новые значения и заголовки с теми же календарными смещениями, затем определяет процентные колонки по новой шапке и форматирует перенесённые участки. Формат процентов primary legacy, округления, расчётные сопоставления и сохранение исторического хвоста не изменены. Сравнение int/float точное по числовому значению, без допуска; bool и текст остаются отдельными типами. Файлы исходного legacy-архива только читались, не запускались и не изменялись.

138 тестов прошли на точном Python финального кандидата. Новые проверки включают холодную/неверную старую шапку, три одинаковых расчёта до/после 15-го числа и месяцы с 28/29/30/31 днём, перенос заголовка процента вместе с месячным срезом, сохранение исторического хвоста и формулы, изменение исходного значения/процентного заголовка с последующей стабилизацией, int/float против bool/текста и локальный цикл запись → два перезапуска → ноль изменений без новых бекапов. Проверки временных GET-сбоев подтверждают максимум три попытки и отсутствие секретов в журнале, отсутствие повторов при TLS/авторизации и единственную попытку POST записи/копирования.

Облачные проверки выполнялись настоящим ShokoAnalytics.exe из собранной поставки через его локальный API, с отдельной рабочей папкой и явным allowlist только созданного QA-ID. Пользователь прямо разрешил тестовые записи в копии. План читался из сохранённого файла, его checksum и состав изменений проверялись перед обычным действием write. Запись проходила штатные проверки актуальности, создание и проверку полной Google-копии и последующую сверку; моки, подмена бекапа и отключение защит не использовались.

| Сценарий | Результат |
|---|---|
| QA-копия текущей тестовой таблицы | Ровно 10376 преобразований числового нуля в «0.0%», штатный бекап, запись и сверка done; затем 0 / 0 / 0 изменений, включая полный перезапуск EXE, без новых бекапов и записи |
| QA-копия бекапа до большого пользовательского обновления | 176444 изменения, штатный бекап, атомарная запись и сверка done; последующие одинаковые подготовки 0 / 0, последняя после перезапуска EXE |

Проверка была итерационной: первый запуск на только что созданной QA-копии правильно остановился из-за смены Drive.version 10 → 13 при неизменных значениях/формулах и нуле комментариев. Проверка версии не ослаблялась, созданная копия и журнал сохранены. После стабилизации версии новый план успешно записан. На одном повторном чтении получен ReadTimeout — добавлены ограниченные повторы только GET. Большое копирование один раз не подтвердилось за прежние 45 секунд: файл найден чтением по точному shokoBackup-маркеру, исходная QA-таблица не записывалась. POST не повторялся; для нового явно проверенного плана увеличен таймаут copy до 180 секунд. Последующий полный этап бекапа занял около минуты и завершился штатно. Ранние неуспешные попытки не выдаются за успешные, их локальные результаты сохранены.

Для новых QA-копий перед первым планом выдерживалась стабильность серверной версии; это подготовка тестового стенда, не изменение правил приложения. [Drive.version](https://developers.google.com/workspace/drive/api/reference/rest/v3/files) учитывает также невидимые пользователю серверные изменения. Проверки подготовки сопоставляют реальный fingerprint и число бекапов, фиксируя версии отдельно; обычная проверка версии перед облачной записью по-прежнему обязательна.

Нативное окно WebView2 / edgechromium проверено --ui-smoke. Kaspersky включён (GetRealTimeProtectionState=1), исключения/политики не менялись, файлы в службы анализа не отправлялись. Тестовые процессы закрывал сам сценарий после завершения проверок. Входные XLSX/CSV, пользовательские настройки и защищённый vault совпали по SHA256 до/после QA-серий на отдельных копиях; исходная настроенная Google-копия и исторический бекап использовались только как источники. Частные планы, логи, ссылки на QA-копии и результаты запусков остаются в игнорируемом runtime/repeatability. Подробный локальный итог серии и синхронизации настроенной копии — runtime/repeatability/REPORT.md; реальные клиентские данные и токены в Git не включаются. Старая неуспешная пользовательская история не переписывается.
